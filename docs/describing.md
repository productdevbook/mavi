# How the API describes itself

Everything this installation answers is declared as a **value**, not written
down twice. An endpoint is a value; the shape of every body is a value; and
what a client reads — the OpenAPI document, the panel's TypeScript — is
generated from those rather than maintained beside them.

The reason is not tidiness. A second document is one somebody stops updating,
and the moment they do, the description becomes a thing that is *nearly* true —
which is worse than none, because people act on it.

## What is declared

    server/mavi-content/src/lib.rs        the endpoints this domain answers
    server/mavi-content/src/described.rs  the bodies those endpoints name

Beside each other on purpose: somebody changing one sees the other.

An endpoint says its method, its address, its stable name, what it takes, what
it answers with, which refusals a caller can expect, and whether it changes
anything. A shape says its fields, each with a type, a sentence, and two
separate facts that are easy to confuse.

## The two facts that are not one fact

**What may be left out** and **what may be nothing** are different, and a
client that cannot tell them apart crashes on one of them:

| | Sent as | Means |
|---|---|---|
| `excerpt` on a `Writing` | `excerpt: string \| null` | always there, sometimes nothing |
| `tags` on a listing | `tags?: Term[]` | may not be there at all |

## What is not described, deliberately

- **What a site decided its own fields are.** A writing's `fields`, a form's
  answers. Describing them would be inventing them, and a generator acts on
  the invention. They are `unknown`, and the object they sit in has no
  `properties` at all — saying `properties: {}` instead is how a generator
  comes to refuse every field a site added.
- **An upload.** What a file is gets decided by reading it, not by anybody
  declaring it. It is `application/octet-stream` with `format: binary`, and
  `Blob` in TypeScript.
- **A writing's `kind`.** Whatever a site decided a thing is. A CMS whose
  kinds are fixed at compile time is a CMS for one site — so `kind` is text,
  while a term's `sort` really is a choice between two and says so.

## The checks that keep it true

None of this is believed. Each of these is a test:

| | |
|---|---|
| Every endpoint says everything about itself | a hole is a name, not a guess |
| No two endpoints are one route | two paths of one shape with differently-named holes is a router that refuses to start |
| No two endpoints have one name | a generated client would have one method calling whichever came second |
| Everything described is reachable | `Site::not_reachable` must come back empty |
| Every body an endpoint names is described | it was a hundred and one that were not, once |
| Every `$ref` in the document resolves | catches a reference written wrongly |
| Nothing is described that nothing refers to | a type in every client that no method returns |
| No two shapes answer to one name | found `File` meaning both an upload and a file in a project |
| **What is described is what is sent** | a real value through the same serialiser a caller reads, its fields compared with what is declared |
| No two endpoints are one assistant tool | `.` and `-` both become `_`, so two names can collide |

The last-but-one is the one that matters most. A hand-written description that
nothing checks is a description that drifts, and everything above it only
proves the description is *consistent* — not that it is *true*.

## What comes out

    /openapi.json                 the description, for anything that reads one
    client/src/api/mavi.ts        the panel's types and its call map

The second is generated by a test — `cargo test -p mavi-everything --test
described` — which writes the file and then compares it with what was there.
It is committed, so the panel builds without a code generator in its way, and
it cannot go stale without the build going red. When it does, CI hands the
corrected file back as an artifact: what somebody needs at that moment is the
new file, not a message telling them the old one is wrong.

## Adding something

1. Declare the endpoint beside its domain's others.
2. Declare the bodies it names in that domain's `described.rs`.
3. Write the test that puts a real value through the serialiser and compares.
4. Run the tests. The panel's types are rewritten; commit them.

Steps 2 and 3 are not optional and the build says so: an endpoint naming a
body nobody describes fails, and a body described and never compared is a
description waiting to drift.
